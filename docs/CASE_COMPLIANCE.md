# QORAI — соответствие исходному кейсу

23.09.2026, итерация коррекции спроса. **Кейс выполнен частично.** Реализованы прогноз, календарь, условная закупка, черновик/CSV, оценочная компенсация возможных потерь и ограничение крупных документов. Последние две функции — алгоритмы на выданных данных, но не доказательство истинного потерянного спроса или идентификации одного клиента.

Первичный источник — выданный `Логистика_Электрокомплект_ТЗ.docx`, русская версия, раздел 7 «Must have». SHA256: `235E26125789A8199A0788DFB54727D6E16BC052A45717613A594DFEE40E8CAF`. P025–P029 — номера абзацев OOXML, не страницы. Прошлый аудит реального Claude Fable сохранён локально в ignored outputs; он относится к версии до двух новых алгоритмов. Текущие формулы описаны в [ALGORITHM](ALGORITHM.md), код — [demand.py](../smartbuyer/demand.py).

## Пять обязательных требований

| Требование оригинала | Реализация | Статус и граница доказательства |
|---|---|---|
| 1. Предусмотренные данные влияют на потребность; изменение источника отражается в результате (P025) | Месячные продажи, остаток/бронь, поставки, явная политика, документные количества и месячные остатки участвуют в цепочке расчёта. | **Частично.** 10 из 12 файлов разобраны; готовые таблицы сезонности не применяются, категория сама не задаёт политику. Нет полной сверки всех источников по складам. |
| 2. Сезонность и устойчивый рост; сезонный товар не сводится к среднему (P026) | Прошлогодний месяц × динамика трёх месяцев; рядом средний кандидат и сравнение на общей прошлой выборке. | **Алгоритм реализован; качество условно.** Автовыбор по MAE может выбрать среднее. Исторический выбор не доказывает будущую точность или устойчивый рост. |
| 3. Компенсация упущенного спроса при подтверждённом stockout (P027) | Нулевой начальный месячный остаток и низкие продажи запускают оценку относительно прошлых месяцев с положительным остатком; сезонный аналог ограничивает базу. | **Реализована оценочная версия, требование частично.** Есть увеличение скорректированного спроса при выполнении условий. Ежедневной доступности/подтверждённых интервалов нет: нулевой срез не доказывает отсутствие весь месяц. |
| 4. Выявление/исключение разового крупного заказа, включая одного клиента (P028) | Положительные расходные документы агрегируются по товару; медиана/MAD выделяют избыточную часть, её доля корректирует месячную базу. | **Реализована документная оценка, требование частично.** Нет client ID, поэтому несколько документов одного клиента не объединяются. Размер не доказывает разовость. Несверенные источники связаны долей, не абсолютным вычитанием. |
| 5. Список по поставщикам с объяснением каждой позиции (P029) | Положительные условные расчёты объединяются в черновик; серверный CSV сохраняет количества, политику, источники и допущения. | **Реализован основной путь.** Список собирается из выбранных SKU; полнота всех необходимых закупок и совместимость с учётной системой не доказаны. Реальной отправки/утверждения заказа нет. |

MOQ/условия поставщика, приоритизация, графики по категориям и автоматическая отправка в оригинале опциональны; компенсация stockout и исключение крупных заказов — обязательны. QORAI ничего поставщику не отправляет. Несмотря на разрешённые оригиналом синтетические тесты, выполняется более позднее решение владельца: новые бизнес-данные не создаются.

## Данные и проверенное покрытие

- Источники: только 12 выданных XLSX, дата среза 22.09.2026, 3045 SKU (582 SystemElectric / 2463 IEK).
- **10 файлов разобраны**, две готовые таблицы коэффициентов сезонности зарегистрированы по SHA256 без применения. Все ячейки каждого разобранного файла не объявляются использованными.
- Месячные остатки сопоставлены 559 SystemElectric и 2456 IEK; это снимки начала месяца, не текущий склад IEK и не ежедневная доступность.
- Операции имеют колонки Дата, Номер, Документ, Код, Номенклатура, Ед., Склад, Количество. Отдельного клиентского идентификатора нет.
- Потоково прочитано 77313 строк SystemElectric и 171604 IEK. Принято 76948 и 171457 строк положительных расходных накладных соответственно; сопоставлены 548 и 2138 SKU.
- Исключено 439 неположительных/некорректных строк, 11 нерасходных/служебных, 62 с несопоставленным/неоднозначным кодом. Отрицательная строка не автоматически считается возвратом. Номера документов в API не раскрываются.
- Строки одного документа суммируются; `document_count` считает документы, не строки. Точное равенство строки не позволяет узнать, является ли она ошибочным дублем или отдельной строкой — выдуманная дедупликация количеств не применяется.
- Исходные месячные продажи и SHA256 всех 12 файлов сохранены. Пустое значение не превращается в ноль. Неизвестные сроки, клиентские обязательства и дни отсутствия не генерируются.

## Что подтверждают проверки

Импорт: **15 passed / 0 skips / 40.98s**; отдельная загрузка набора — 30.56s. Проверены точное соответствие месячным источникам, агрегация документов, несколько строк/складов одного документа, отсутствие повторного учёта брони, исключение неподходящих строк/будущего, неоднозначные ключи и неизменность SHA.

Независимый полный прогон текущего кода: **161 passed / 0 skips / 233.19s / exit0** на выданном наборе. Он заменяет промежуточные focused122/addressed48 как общий итог; складывать наборы нельзя. Browser-приёмка новой версии фиксируется отдельно в [QA_REPORT](QA_REPORT.md), не подменяется прежними проверками Q36.

MAE считается относительно исходных наблюдаемых продаж. Без подтверждённых скрытого спроса/дней отсутствия нельзя утверждать точность компенсации. Не заявлены процент выигрыша, достигнутая экономия или выполнение 100% кейса.

Финальный cached forecast CSV проверен по **всем 3045 строкам: stockout_positive_items=0**. Алгоритмическая ветка компенсации проходит unit-тесты, но положительного source-примера нет. Это ограничивает подтверждение must-have3; крупные документы действительно меняют расчёт, но не доказывают клиентскую разовость. Пороги ради demo не изменялись.

## Оставшиеся проверки и развитие

1. Согласовать область склада, знаки и полноту операций относительно месячной базы; откалибровать пороги на подтверждённых разовых продажах.
2. Получить ежедневную доступность/подтверждённые интервалы для проверки оценки потерь; месячные снимки не заменяют эти данные.
3. При появлении client ID проверять клиента, а не только документ; учитывать отдельные клиентские обязательства и не удваивать бронь.
4. Отдельно проверить качество на отложенных периодах и одинаковых внешних фактах; MAE на выборке выбора метода не равно будущей экономии.
5. Учесть жизненный цикл/вывод из ассортимента: длительный нулевой остаток может давать оценку потерь, пока доступны прошлые опоры. Уточнить, идентичны ли timestamps строк одной накладной; текущий точный ключ может разделить документ при разных датах/времени строк.

Новый настоящий Claude Fable-аудит текущего кода завершён с **exit0 за 182.746s**, 5419 оценочных входных токенов, `tools=[]`; блокирующих замечаний по отчёту исполнителя/приёмке ведущего нет. Это статическая проверка переданного кода, не исполненные Fable тесты или browser QA. Исторический аудит первой версии имел неоднозначную квитанцию `status=failed`, `exit_code=null`; она не относится к новому успешному запуску.
