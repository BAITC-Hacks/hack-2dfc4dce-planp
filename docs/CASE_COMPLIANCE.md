## Покрытие импорта и реальные результаты

`GET /api/bootstrap` показал 12 зарегистрированных источников: **8 `read_cached_values` и 4 `not_parsed`**. Не разобраны обе таблицы операций (`transactions`) и обе таблицы сезонности (`seasonality`). Для них [data.py:66–71](../smartbuyer/data.py#L66) сохраняет имя/хеш, затем возвращает пустой набор строк. Даже статус `read_cached_values` не означает, что каждая ячейка влияет на прогноз: из истории остатков, например, извлекается единица товара.

Корректная формулировка интерфейса: «12 файлов зарегистрировано; 8 разобрано, 4 только проверены по хешу». «Все 12 проанализированы» или «учтены все источники в расчёте» — недоказанные заявления.

В ответе API: 3045 SKU; дата среза 22.09.2026; цель октябрь 2026; 758 сезонных прогнозов `provisional`, 2287 `blocked`, 3331 общая историческая точка. `order_blocked_items=3045` относится к исходному CLI-отчёту, не к каждому возможному условному API-сценарию.

На `SystemElectric::ATN544045` октябрьский сезонный прогноз 152.23618, средний 89.28631; MAE на одинаковых шести точках 67.52910 и 40.00181 соответственно. Это не доказательство выигрыша сезонного метода.

На исходном `ATN540126` перенос ETA существующего прихода 120 единиц с 24.09 на 08.10 меняет условный заказ с 0 на 36. Политика L2/H30/страховой запас7/MOQ0/auto введена явно для технической проверки, не объявлена политикой компании; исходная ETA без года остаётся неизвестной. Это проверка чувствительности, не компенсация stockout.

## Минимальные следующие шаги без новых бизнес-данных

Это предложения для отдельного назначения, не выполненные изменения. Текущий аудит не разрешает менять ядро.

1. **Массовый расчёт — наиболее достижимое улучшение за ограниченное время.** Повторно использовать существующий `/api/plan` для явно выбранных исходных SKU и одной явно подтверждённой политики; собрать все статусы, включая blocked, и передать только сохранённые result IDs в существующий экспорт. Не подставлять общую политику автоматически по категории. Проверка: равенство одиночному расчёту, отсутствие дублей, сохранение blocked, сброс после изменения политики/reload. Новое серверное расчётное ядро не требуется.
2. **Разовые операции — сначала отдельная диагностика, без изменения закупки.** Разобрать реальные колонки операций, согласовать знак/тип документа, единицу, склад и SKU; сопоставить месячные суммы одного исходного SKU с основной базой. Только после согласования охвата можно добавлять проверяемые кандидаты крупных документов с явными параметрами. До подтверждения кандидаты не вычитаются из месячных продаж. Ограничение месяца по медиане без проверки сезона не принимается как безопасное выполнение требования4; клиентская часть остаётся открытой без client ID.
3. **Stockout — положительный результат сейчас не доказуем.** Сделать явный статус отсутствия ежедневной доступности/интервалов по источнику и nullable результат компенсации. Для алгоритма запросить подтверждённые SKU/склад/период, доступные и отсутствующие дни, продажи на доступных днях. Месячные остатки не превращать в придуманные дни stockout. За примерно50 минут можно улучшить диагностику и подготовить контракт входа; закрытие требования3 такими действиями обещать нельзя.

При бюджете около50 минут разумно сначала закрыть видимость покрытия и массовый путь с адресными тестами; исследования операций выполнять ограниченно и не смешивать неподтверждённый новый спрос с текущим расчётом. Полный кейс остаётся частичным до реализации и проверки требований3/4 на пригодных данных.

## Ограничения внешнего аудита

Fable получил 4273 оценочных токена, tools=[], retry0; ответ получен за56.8с. Внешняя команда завершилась с exit0, но квитанция launcher содержит `status=failed`, `exit_code=null`; успешное завершение самого дочернего Claude этой квитанцией не доказано. Текст ответа существует и приведён без правок в локальном отчёте. Проверка схемы XLSX выполнена Codex после ответа и исправляет слишком широкое утверждение Fable об отсутствии строк операций. Тесты и браузерная проверка отмечаются отдельно в [QA_REPORT](QA_REPORT.md).
