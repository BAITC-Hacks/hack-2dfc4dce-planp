## 3. Минимальный интерфейс между потоками

Интегратор фиксирует plain dict / JSON из TECH_SPEC; один набор ключей для CLI, будущих API/UI и экспорта, без лишнего `contracts.py` и сложных общих схем.
Для будущего web-слоя предложены маршруты `POST /api/import`, `POST /api/forecast`, `POST /api/backtest`, `POST /api/scenario`, `GET /api/export`; сейчас это контракт, не задача создавать все маршруты.
Import возвращает dataset_id и issues/источники; forecast/backtest принимают dataset_id, source_id, cutoff и только разрешённые параметры.
Scenario принимает ID реально существующей поставки и scenario_eta после действия менеджера; исходный dataset неизменен.
Ответ расчёта разделяет forecast/risk/order rows и статусы; ошибка формата — структурированная ошибка, недостаток бизнес-данных — blocked строки с value=null.
Экспорт выбирается по результату/сценарию, не пересчитывает другой набор: единицы, источники, statuses/reasons и null совпадают с показанным результатом.
Платный LLM не нужен для ядра, API и базового UI. Предлагаем использовать установленный Python/FastAPI/openpyxl; UI-стек зависит от выбранного экспорта Stitch.

## 4. Ограниченный бюджет и условия остановки

На момент постановки владелец сообщил около 2ч22мин до окончания; фактический остаток проверяется перед запуском работ, дедлайн не переносится.

Этапы перекрываются по готовности контрактов; сроки — бюджет, не обещание. После 17:30 новые функции не добавляем, исправляем блокеры и проверяем сдачу.
Расчёт закупки/календаря не отнимает время у ядра при отсутствии L/H/политики/обязательств; корректный blocked — результат проверки допустимости, не исполненное требование закупки.
Клиентские партии/бронь/приёмка как модули, ночное обучение, собственная синтетика и доказательство денежной экономии не входят в этот план.
