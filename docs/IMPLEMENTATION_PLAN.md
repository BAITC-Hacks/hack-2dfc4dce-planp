## 1. Замораживаем объём

Основной путь: импорт → прогноз → дефицит по датам → объяснимый заказ по поставщикам → экспорт.
Три представления: «Сегодня», «Рекомендации и черновик», «Данные и допущения»; дополнение только одно — изменение ETA.
Брони, приёмки и клиентские партии — входы/подписанные демо-события, не отдельные операционные модули.
За пределами первого объёма: полная ERP, биллинг SaaS, ночное обучение, реальные отправки поставщику и автоматическая отмена обязательств.
Сохраняем принятый владельцем приоритет крупному клиенту; показываем затронутые обычные продажи и другие обязательства.
Формулы-кандидат и ограничения: [LOGISTICS_PLAN.md, раздел 17](LOGISTICS_PLAN.md); это ещё не валидированный алгоритм.

## 3. Минимальный контракт данных до параллельного кода

| Набор | Минимальные поля и смысл |
|---|---|
| Товары | `sku`, поставщик, единица, категория, упаковочная кратность, MOQ с признаком «неизвестно/нет ограничения» |
| Продажи | SKU, склад/охват, период или дата/тип/строка документа, количество, источник и дата отсечения |
| Исходный остаток | SKU, склад, единица, `as_of`, полный отчётный/сверенный остаток, резерв, свободный; явная связь и сверка, не три слагаемых |
| Поступления | Идентификатор цепочки, SKU/склад, оставшееся открытое количество по статусам, ETA либо «неизвестна», подтверждение |
| Обязательства | Идентификатор цепочки, SKU/склад, оставшееся количество, дата исполнения, `regular/additive/unknown`, выделение; исполненное исключено |
| Параметры | План роста либо метод тренда, полный срок `L`, горизонт `H`, дни покрытия категории, подтверждённые периоды недоступности |

Все наборы сохраняют происхождение, единицы и свежесть; дата компьютера не заменяет дату источника.
Нет клиентского ID/дневной доступности — помеченные синтетические тесты, не заявление, что нашли конкретного клиента или исторический дефицит.
Неясные отрицательные движения, пустые значения, кратность и классы обязательств не подменяются нулями/единицами без основания.
Источники продаж расходятся: выбор базы подтверждается явно; до ответа ментора показываем временный источник и ограничение достоверности.
Выход расчёта: выбранные входы/допущения, датированный баланс, первый риск, количество/срок/причина по SKU и поставщику, предупреждения, версия сценария.

## 4. Параллельные потоки после общего контракта

- Поток A — данные и детерминированный расчёт: проверка схемы, адаптеры файлов, прогноз, календарь, рекомендации, экспорт и числовые тесты.
- Поток B — интерфейс выбранного Stitch-дизайна: три представления, импорт/ошибки, сценарный ETA, график, объяснение и предпросмотр экспорта.
- До старта ведущий назначает непересекающиеся файлы; общий контракт и синтетические примеры меняются согласованно, не двумя писателями одновременно.
- Интеграция идёт на золотых примерах ниже; расчёт не зависит от LLM, а интерфейс не пересчитывает числа второй несовместимой формулой.
- Среда проверена ведущим: Python, openpyxl 3.1.5, FastAPI 0.115.6, uvicorn 0.32.1 и pytest 9.0.2 уже установлены; Node/npm доступны.
- Предлагаем Python-расчёт и FastAPI для API/раздачи интерфейса, UI-стек — по выбранному результату Stitch. Один процесс, без новой БД/платного LLM в ядре; сейчас ничего не устанавливаем и не создаём scaffold/auth/микросервисы.

## 5. Приёмка: числа, данные и пользовательский путь

| Проверка | Ожидаемый результат |
|---|---|
| Пять требований кейса | Влияние всех входов; сезон/рост; подтверждённый дефицит; защита от разовой крупной продажи; объяснимые группы поставщиков |
| Потребление прогноза | `F=100, R=30, E=40 → D=140`; `R=130 → D=170`; месячный `max` не повторяется по дням |
| Кандидат крупной аномалии | 22 согласованных прошлых операции: 20×10 и 2×14 → `Q1=Q3=10`, порог 50; новая 180 → кандидат 50/избыток130, не подтверждённое исключение. При n=15 — 180 без очистки; прошлогодний сопоставимый документ200 → сезонный кандидат до проверки |
| Компенсация отсутствия | Закрытый месяц: `A25/Z5/U0/C250 → потеря50/скорректировано300`; `A23/Z5/U2/C230 → частичная оценка280`, не полная истина; `A0 → неизвестно`. Это арифметические эталоны, не запущенные тесты |
| ETA: базовый синтетический пример | На конец 23.09: полный остаток 1000, бронь 600, свободно 400; приход 800 на 26.09; регулярный спрос 120/день с 24.09; дополнительная партия 600 на 27.09; баланс 27.09 = 720 |
| ETA: перенос на 01.10 | Прогноз на 27.09 = −80, а исходный учтённый остаток остаётся 1000; клиент600 — `additive`, не входит в regular120/день |
| Двойной учёт | Бронь/заказ/выдача одной цепочки не повторяют спрос или списание; задержка поставщика не создаёт второй заказ на весь старый объём |
| Просрочка и частичность | Неисполненная просрочка учитывается один раз отдельно; вход частичной поставки не выдаёт остаток всей партии за полученный |
| Качество и свежесть | Видны дата среза, неизвестный источник/ETA/MOQ/кратность; неизвестная кратность не превращается в 1 |
| Схема и экспорт | Некорректный файл не заменяет валидный набор; в экспорте совпадают SKU, единицы, количество, поставщик, причина и видимые допущения |
| Браузерный smoke | Импорт → риск → изменение ETA → объяснение → черновик → скачанный экспорт с проверенным содержимым; состояния ошибок и клавиатура работают |

Программные тесты пока не выполнены: таблица — будущие критерии, а синтетическая арифметика уже согласована как тестовый эталон.
Сравнение с простым методом: один источник, классификация, фактический внешний тестовый спрос, остатки и политики; меняется только прогноз.
Оцениваем временную проверку MAE, непокрытые единицы, средний запас и объём заказа; не рисуем ROI и не считаем пользу относительно собственного прогноза каждой модели.
Кандидаты детектора/компенсации после критики Fable записаны в основном плане (§18); пороги не калиброваны. Без согласованных операций и истории доступности реальные критерии не объявляются решёнными, даже если арифметическая синтетика проходит.
